# V1: SQL verification report (Seller migrations and rate limits)

Status: verified against the best local approximation of production. **Not yet verified against the real schema**: the live Supabase project cannot be reached from the repo, so `supabase/baseline/live-schema.sql` does not exist yet. Until it does, do not describe the file as "verified on the real schema".

## What was tested
Command: `node scripts/verify-baseline.mjs --synthetic` (PGlite, no network, no Docker).

The approximation is built from:
- a Supabase prelude (roles `anon`/`authenticated`/`service_role`, schemas `auth`/`storage`/`extensions`, `auth.uid()`, `extensions.uuid_generate_v4()`): `supabase/tests/supabase-prelude.sql`;
- the 11 tables in `docs/marketplace/schema-baseline.json` with their real types, lengths, defaults, NOT NULLs and foreign keys (varchar lengths, `extensions.uuid_generate_v4()` defaults), plus stubs for `currencies` (seeded), `recipients`, `expert_service_schedules`, `exchange_rates`;
- every older migration in `supabase/migrations/` (hub cart, avatar/storage, Bitbanker, marketplace lifecycle, notify gate, cancel/restore cart), all of which apply without error;
- seed rows chosen to hurt the backfill: two vendors with the same service line and slug, an expert with no slug, two experts with the same slug, a product with no vendor, orders on three lines (vendor quote, expert quote, empty quote).

Checks, all passing:
1. Pre-checks at the top of the deploy file: required tables true, PG 15+, every column the migrations read exists, no name clashes, sizes.
2. `seller-portal-all.sql` then `rate-limits.sql` run clean.
3. Second run: schema fingerprint (columns, constraints, indexes, triggers, function bodies, views, RLS flags, table and function grants) and row counts identical.
4. The deploy file equals the migration files applied one by one; the migration files are also re-runnable one by one.
5. Verify queries all 0 (vendors, products with a vendor, experts, merchants shared by several vendors or experts, orders whose quote names a vendor or expert).
6. `pg_trgm` indexes are created (extension loaded in the harness).
7. Existing suites still pass: `npm run test:merchant` (34 SQL/TS tests) and `npm run test:marketplace` (11).

## What changed
No migration had a hard error on the approximation. Changes are defensive:
- `20261016100000_merchants_foundation.sql`
  - Vendor and expert backfill rewritten as an idempotent loop. Before, two vendors with the same `(service_line_slug, slug)` would silently share one merchant (the `on conflict do nothing` plus link-by-slug), and a null slug would have produced a null link. Now each unlinked row gets its own merchant (slug falls back to `<base>-<first 8 of id>`), nothing is linked by slug lookup.
  - Order backfill only updates rows that resolve to a merchant (it used to rewrite every unresolved order to null each run).
- `set local lock_timeout = '5s'` after `begin` in foundation, ledger, notifications, reviews, messages and discovery: a part that cannot get a table lock fails fast and changes nothing, instead of queueing and blocking every other query on that table. Re-run it.
- `20261016160000_discovery.sql`: the trigram index block is wrapped in an exception handler (an extension installed in a schema off the search path no longer aborts the part).
- `supabase/deploy/seller-portal-all.sql` regenerated by the new `scripts/build-seller-deploy.mjs` (`--check` fails if a deploy file is stale). New header explaining re-run behaviour; four pre-checks (booleans including Postgres 15, missing columns must be zero rows, name clashes must be zero rows on first run, table sizes); stricter verify block (products only counted when they have a vendor, shared-merchant and order checks, one informational line).
- `supabase/deploy/rate-limits.sql` regenerated from its migration with a one-line header (SQL unchanged).

Already safe, checked and left alone: no `alter column ... type`; every `not null` column add has a constant default (metadata-only on PG 11+); every `create` uses `if not exists` or `or replace`; triggers use `drop trigger if exists` first; seeds use `on conflict do nothing` / `where not exists`.

New files: `scripts/verify-baseline.mjs`, `scripts/build-seller-deploy.mjs`, `supabase/tests/supabase-prelude.sql`, `supabase/scripts/capture-live-schema.md`, this report. Place for the owner's dump: `supabase/baseline/live-schema.sql`.

## What stays unknowable without the live dump
- Whether production really has the marketplace lifecycle tables and which columns/constraints production has beyond the repo's baseline (the pre-check 1 and 2 results in the SQL Editor will say). The 17 tables with no DDL in the repo are only approximated; unknown extra columns, NOT NULLs or triggers on `users`, `hub_vendors`, `hub_products`, `expert_profiles`, `expert_services` could clash.
- Name clashes with objects that exist in production but not in the repo (`reviews`, `audit_log`, `payouts`, `favorites`, `settings`-like tables). Pre-check 3 lists them; `create table if not exists` would silently skip a table with a different shape and a later index or function would then fail (the part rolls back).
- Postgres version (the file needs 15+; pre-check 1 reports it) and whether `pg_trgm` is installed or installable.
- Real row counts and data shapes (null slugs, duplicate slugs, orphan products, orders whose quote has no vendor). The backfill handles the shapes tried here; the verify block reports what remains.
- Behaviour under production load and locks: the 5 second lock timeout protects writers, but index builds on `hub_products` and `marketplace_orders` take brief write locks; run outside peak hours. Row counts in pre-check 4 show whether that matters (it does not for tables under tens of thousands of rows).
- Permissions/default privileges of the real project (the prelude copies Supabase's defaults).
