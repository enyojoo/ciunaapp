# API and data build plan

Scope: what `api/` and Postgres need so every approved design card can be built. Read-only analysis of the repo at `main`. Sources: `design-system/cards.json`, every `components/*/README.md` Upgrade section, `guides/80-decisions.md`, `docs/seller-portal-*.md`, `docs/marketplace/*`, `api/app/api/**`, `api/lib/**`, `supabase/migrations/**`.

Status key: **exists** (route and table shipped and tested), **partly**, **missing**. Anything a card marks New is a proposal (`guides/80-decisions.md`); `docs/design-to-build-plan.md`, which that guide names as the gate, does not exist. This file and `launch-readiness.md` are the closest substitute; confirm each New feature with the owner before its package starts.

## 0. Findings that shape everything

1. **Core tables are not in migrations.** `docs/marketplace/schema-baseline.json` captures 13 tables (`users`, `transactions`, `hub_products`, `hub_vendors`, `hub_carts`, `hub_cart_items`, `hub_order_items`, `expert_profiles`, `expert_services`, `expert_service_slots`, `expert_bookings`, `payment_methods`, `delivery_addresses`). Migrations only `alter` them (`20261016100000_merchants_foundation.sql` adds `merchant_id`, `review_status`, `translations` to `hub_products`; `20260925090000` alters `hub_vendors`, `expert_services`). A fresh Postgres cannot run the migration chain without `supabase/tests/marketplace-baseline.sql`, which is test-only and not a bootstrap.
2. **Many tables the API reads have no DDL anywhere in the repo**: `admin_users`, `system_settings`, `settings`, `kyc_submissions`, `recipients`, `currencies`, `exchange_rates` (only metadata added), `referral_rewards`, `referral_payout_requests`, `assistant_requests`, `login_attempts`, `transaction_status_history`, `crypto_wallets`, `crypto_receive_transactions`, `hub_service_lines`, `expert_service_schedules`, `expert_service_weekly_rules`. They exist only on the live project. `api/lib/login-attempts.ts` and `kyc-service.ts` even tolerate the table being missing.
3. **Office authorisation is inconsistent.** `api/lib/admin-roles.ts` defines the role matrix, but `adminCan` is used only through `api/lib/merchant/http.ts` (merchant, KYB, fee, payout routes). Roughly 24 legacy `api/app/api/admin/*` routes call `requireAdmin` (any admin) with no permission check: `kyc`, `users`, `transactions`, `exchange-rates`, `settings`, `currencies`, `admin-users`, `referral-payouts`, `assistant/requests`.
4. **No API versioning, no rate limiting, no shared contract.** `api/proxy.ts` only sets CORS and `no-store`. Clients hand-write fetch types.
5. **PIN is client-only.** `mobile/lib/secure-storage.ts` holds PIN secrets in SecureStore; the server has no attempts counter.
6. **Maintenance is web-only.** `web/middleware.ts` and `web/app/maintenance/page.tsx` read `maintenance_mode` through `GET /api/platform/public-flags`. The API, Expo app and Seller ignore it.

## 2. Migration ordering

Order matters because `20261016*` migrations reference baseline tables.

0. **`20260901000000_baseline.sql`** (new, earliest): idempotent `create table if not exists` for the 13 baseline tables plus the 17 untracked tables in finding 2, derived from a schema-only `pg_dump` of the confirmed staging project (not from `schema-baseline.json`, which lacks constraints, triggers, policies and grants). On an existing database it is a no-op; on a fresh one it makes the chain runnable. Verify with `supabase db diff` against production schema: diff must be empty.
1. Existing chain, unchanged order: hub cart, avatar, Bitbanker (3), exchange metadata, marketplace lifecycle, RLS ensure, notify gate, cancel restore, then `20261016100000` to `20261016160000`.
2. New migrations, one per package (section 3), each timestamped after `20261016160000`, additive only: no drops, no column type changes, no renames. Columns added `null`-able or with a default.
   - `reason_templates`, `kyc_levels`, `users.kyc_level`, `kyc_submissions.rejection_code`
   - `exchange_rate_history`, `exchange_rate_changes`
   - `catalog_reviews`, `order_notes`, exception reason constraint (`not valid` then `validate` in a later migration)
   - `push_devices`, `notification_prefs`, `customer_outbox`
   - `order_message_translations`
   - `support_threads`, `support_messages`
   - `referral_limits`
   - `payout_rails`, `payout_attempts`
3. Policy: ship the DDL before the code that uses it; ship code that tolerates the old schema for one release (the `search` route already does this for rating columns).

## 4. Shared types and versioning

**Shared contract.** Today clients hand-write types (`packages/shared/src/marketplace`, `hub`, `types`). Plan:

1. Add `packages/contract` (or extend `@ciuna/shared`) with one zod schema per endpoint (the API already depends on `zod`). Export `z.infer` types and a request/response map. The API route validates input with the same schema; clients import types and optional runtime parsers.
2. Generate `api/openapi.json` from those schemas (`zod-to-openapi`) in CI and publish it as a build artefact. Contract tests: for each route, call it against a test database and parse the response with the shared schema; fail on drift.
3. Error shape: one `{ error: CODE, message?, details? }` shape. `MarketplaceError` codes (`PRICE_CHANGED`, `QUOTE_EXPIRED`, ...) are already stable strings; document them as the enum. Do not rename codes.
4. Money in responses: `{ amount: string, currency }` decimals or integer minor units, never floats; match `packages/shared/src/money`.

**Versioning for the Expo app (cannot be force-updated).**

- Add `/api/v1/` as an alias namespace via `next.config.mjs` rewrites; clients ship pointing at `/api/v1`. Existing `/api/*` paths keep working as v1 forever. A v2 is created only for a breaking change and the old path stays up until store analytics show under a stated threshold (decide in launch-readiness go/no-go).
- Clients send `X-Client: ios|android|web|seller|office`, `X-Client-Version`, `Accept-Language`. The API logs them (no PII) and can answer with `X-Min-Client-Version` and `X-Deprecation`.
- `GET /api/platform/public-flags` gains `minSupportedVersion { ios, android }` and `updateUrl`. The Expo app shows a blocking "Update required" screen only when below the minimum; the minimum is raised only when a server rule truly cannot be kept compatible.
- Backwards-compatibility rules (enforced by review and by contract tests that replay recorded responses of the last two shipped app versions):
  1. Responses: only add fields; never remove, rename or change the type or meaning of a field. Add enum values only if clients treat unknown values as a neutral default (`StatusBadge` already falls back to neutral).
  2. Requests: new fields optional with server defaults; never make an existing field required.
  3. Errors: keep codes and HTTP status. A new error code must have a fallback message path (`api/lib/api-error-message.ts`).
  4. Idempotency keys and quote or payment contracts (`/api/hub/checkout`, `send/quotes`, `send/transfers`) freeze: replay protection depends on stable hashing of the request body.
  5. Database changes are additive (section 2); a column is dropped only after two release cycles with no readers.
  6. New customer features appear behind feature flags in `public-flags` so an old app never sees a half-built screen; hide-by-default keys.
  7. Webhook and cron paths are never versioned.
- Keep a fixture folder `api/tests/compat/<app-version>/` with recorded request and response pairs for each store release; the CI job replays them against HEAD.
- Release safety: EAS builds record the API contract hash; a release is blocked if the contract diff against the last shipped hash contains a removal.
